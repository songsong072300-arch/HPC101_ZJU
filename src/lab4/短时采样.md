我采用的是“缩短物理演化 + 分阶段运行 + 限时 perf 采样”，并没有每次都执行正式的 t=40 端到端任务。

  ## 1. 缩短演化时间

  正式 CPU 输入是：

  Final_Evolution_Time = 40.0

  开发和采样时临时改成：

  Final_Evolution_Time = 2.0

  这样程序只演化两个时间步，足够让主要函数被反复执行并形成热点样本。

  当前项目已经是：

  Final_Evolution_Time = 2.0

  正式测试前必须恢复：

  Final_Evolution_Time = 100.0 if GPU_Calculation == "yes" else 40.0

  ## 2. 先生成运行目录和初值

  通过：

  ./run.sh --twop-cache

  生成：

  GW250118/AMSS_NCKU_output/
  ├── ABE
  ├── TwoPunctureABE
  ├── Ansorg.psid
  ├── input.par
  └── ...

  --twop-cache 的作用是缓存 TwoPuncture 初值。后续分析 ABE 时可以跳过约两分钟的初值求解。

  它只适用于：

  - 调试 ABE；
  - ABE 性能采样；
  - 没有修改初值物理参数的情况。

  正式端到端计时不能使用缓存。

  ## 3. 直接运行 ABE

  初值和 input.par 已经生成后，不必每次都经过完整 Python driver，可以直接进入输出目录：

  cd GW250118/AMSS_NCKU_output

  用30个 MPI rank、每 rank 1线程运行：

  mpiexec --allow-run-as-root \
    -n 30 \
    env OMP_NUM_THREADS=1 \
        OMP_PROC_BIND=close \
        OMP_PLACES=cores \
    ../../build/ABE < /dev/null

  这样不会重复运行 TwoPuncture、绘图和 Python 后处理，只测 ABE。

  < /dev/null 很重要，因为 ABE 运行过程中会检查终端输入；重定向可防止无人值守运行时阻塞。

  ## 4. 使用 perf record 快速采集热点

  实际使用的核心命令是：

  mkdir -p profiling_results/quick

  cd GW250118/AMSS_NCKU_output

  perf record \
    -m 4 \
    -F 99 \
    -o ../../profiling_results/quick/perf.abe.data \
    -- \
    mpiexec --allow-run-as-root \
      -n 30 \
      env OMP_NUM_THREADS=1 \
          OMP_PROC_BIND=close \
          OMP_PLACES=cores \
      ../../build/ABE < /dev/null \
      > ../../profiling_results/quick/abe_run.log \
      2> ../../profiling_results/quick/perf_record.log

  参数含义：

  - -F 99：每秒约采样99次。
  - -m 4：使用较小的 perf mmap buffer，规避容器中 mlock 限制。
  - -o ...：指定采样文件，避免覆盖其他版本。
  - --：后面的内容都是被采样程序。
  - -n 30：启动30个 MPI rank。
  - OMP_NUM_THREADS=1：避免30个 rank 各自创建30线程。
  - OMP_PROC_BIND=close、OMP_PLACES=cores：控制线程绑定。
  - stdout 和 stderr 分别保存，方便判断 ABE 是否正常推进。

  ## 5. 不必等待程序完整结束

  如果只是寻找热点，可以给采样加超时：

  timeout -k 5 120 \
    perf record \
      -m 4 \
      -F 99 \
      -o ../../profiling_results/quick/perf.abe.data \
      -- \
      mpiexec --allow-run-as-root \
        -n 30 \
        env OMP_NUM_THREADS=1 \
            OMP_PROC_BIND=close \
            OMP_PLACES=cores \
        ../../build/ABE < /dev/null

  含义：

  - 采样120秒；
  - 120秒后先发送正常终止信号；
  - 5秒内没有退出则强制终止。

  这种结果只能用于定位热点，不能用于：

  - 正确性验证；
  - 性能成绩；
  - 完整运行时间比较。

  我当时让它采集了约5分钟，获得：

  138,057 samples
  Total Lost Samples: 0

  样本已经足够，所以发送 Ctrl-C 停止。perf 会正常收尾并写出 perf.data：

  perf record: Captured and wrote ...

  如果手工操作，就是在采样终端按一次：

  Ctrl-C

  不要连续按两次，否则可能导致 perf 来不及完整保存数据。

  ## 6. 生成热点报告

  查看函数自身占比：

  perf report \
    -i profiling_results/quick/perf.abe.data \
    --stdio \
    --no-children \
    -g none \
    --percent-limit 0.2

  保存报告：

  perf report \
    -i profiling_results/quick/perf.abe.data \
    --stdio \
    --no-children \
    -g none \
    --percent-limit 0.2 \
    > profiling_results/quick/perf.abe.self.txt

  参数含义：

  - --stdio：输出文本报告。
  - --no-children：显示函数自身开销，避免调用者累计占比影响判断。
  - -g none：不展开调用图。
  - --percent-limit 0.2：显示占比不低于0.2%的函数。

  查看采样是否完整：

  perf report \
    -i profiling_results/quick/perf.abe.data \
    --stdio \
    --header

  重点检查：

  Samples
  Total Lost Samples
  Event count

  ## 7. 使用 perf stat 判断瓶颈类型

  热点采样告诉我们“时间在哪里”，硬件计数器则解释“为什么慢”。

  命令：

  cd GW250118/AMSS_NCKU_output

  perf stat -d \
    -o ../../profiling_results/quick/perf.abe.stat \
    -- \
    mpiexec --allow-run-as-root \
      -n 30 \
      env OMP_NUM_THREADS=1 \
          OMP_PROC_BIND=close \
          OMP_PLACES=cores \
      ../../build/ABE < /dev/null

  也可以只统计120秒：

  perf stat -d -- \
    timeout -k 5 120 \
    mpiexec --allow-run-as-root \
      -n 30 \
      env OMP_NUM_THREADS=1 \
      ../../build/ABE < /dev/null

  主要关注：

  - CPUs utilized
  - instructions
  - cycles
  - IPC
  - branch-misses
  - L1-dcache-load-misses
  - LLC-load-misses

  当时还检查了容器实际 CPU 配额：

  cat /sys/fs/cgroup/cpu.max
  cat /sys/fs/cgroup/cpuset.cpus.effective

  结果为：

  400000 100000
  0-63

  第一行表示：

  400000 / 100000 = 4 CPUs

  所以虽然 lscpu 显示很多核心，开发容器实际只能使用约4核。30个 MPI rank 在4核上运行会产生大量 MPI 等待，因此这里采到的 MPI 占比不能代表正
  式30核计算节点。

  也可以运行：

  ps -eo pid,etime,pcpu,comm,args | \
    rg '(perf|mpiexec|prterun|/ABE)'

  观察所有 ABE rank 的总 CPU 使用率。

  ## 8. 一步 smoke test 的实现方式

  为了测试代码能否正确运行，同时不覆盖现有结果，我没有修改正式工作目录，而是创建 /tmp 副本：

  smoke_dir=$(mktemp -d /tmp/lab4-smoke.XXXXXX)

  cp GW250118/AMSS_NCKU_output/input.par \
     GW250118/AMSS_NCKU_output/AMSSNCKU_setting_parameter \
     GW250118/AMSS_NCKU_output/Ansorg.psid \
     "$smoke_dir"

  把副本中的结束时间缩短：

  sed -i \
    's/ABE::TotalTime =  2.0/ABE::TotalTime =  0.1/' \
    "$smoke_dir/input.par"

  然后在副本中运行：

  cd "$smoke_dir"

  timeout -k 5 240 \
    mpiexec --allow-run-as-root \
      -n 4 \
      env OMP_NUM_THREADS=1 \
      /home/h3250106538/HPC101/src/lab4/build/ABE \
      < /dev/null \
      > smoke.log 2>&1

  这里设置 TotalTime=0.1，但程序的时间步进粒度使它实际上完成了一个时间步，日志会显示：

  Timestep # 1: integrating to time: 1
  Simulation is successfully done

  查看结果：

  rg "Before Evolve|Timestep|Total Evolve|Total Running|successfully" \
    "$smoke_dir/smoke.log"

  这种方式的优点是：

  - 不修改正式 AMSS_NCKU_Input.py；
  - 不覆盖 GW250118/AMSS_NCKU_output；
  - 不重复运行 TwoPuncture；
  - 一次只验证 ABE；
  - 不通过检查时可以直接查看独立日志和输出。

  ## 推荐的日常命令

  快速热点采样可以直接使用：

  cd GW250118/AMSS_NCKU_output

  timeout -k 5 120 \
    perf record -m 4 -F 99 \
      -o ../../profiling_results/perf.abe.test.data \
      -- \
      mpiexec --allow-run-as-root \
        -n 30 \
        env OMP_NUM_THREADS=1 \
        ../../build/ABE < /dev/null

  cd ../..

  perf report \
    -i profiling_results/perf.abe.test.data \
    --stdio --no-children -g none \
    --percent-limit 0.5

  完整工作流是：

  t=2生成一次输入与初值
          ↓
  直接运行build/ABE
          ↓
  perf采样120秒
          ↓
  生成函数热点报告
          ↓
  修改一个优化点
          ↓
  增量编译
          ↓
  /tmp中跑一个时间步
          ↓
  通过后重新采样
          ↓
  候选版本才跑正式t=40

  这样多数优化迭代只需几分钟，而不需要每次等待完整一小时。
